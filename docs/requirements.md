# Bakery CLI - Requirements Document

## 1. Overview
The **Bakery CLI** is a Go-based command-line tool designed to quickly scaffold new projects. Its primary goal is to provide a standardized, automated way for developers and AI agents to initialize projects using a pre-defined technology stack without having to manually install dependencies or configure boilerplate code.

## 2. Supported Pies (Project Types)
The CLI must be able to generate the following types of projects:
1. **Go CLI Applications**
2. **Go Daemons (Background Services)**
3. **Web Applications** (Go backend with a React frontend)

*(Note: While currently focused on Go, the architecture should be designed flexibly enough to support scaffolding entirely non-Go based projects in the future).*

## 3. Technology Stack Requirements
All generated projects must adhere to the following technology stack:

### 3.1. Go Ecosystem (All Projects)
* **Language:** Go
* **CLI Framework:** [Cobra](https://github.com/spf13/cobra) - mandatory for all Go applications (CLI, Daemons, and Web app backends).

### 3.2. Frontend Ecosystem (Web Applications)
* **Build Tool:** Vite
* **Library:** React
* **Language:** TypeScript
* **Constraints:** No meta-frameworks like Next.js or Remix should be used.

## 4. Initialization Strategy (Registry-Backed Overlay Templating)
The CLI will utilize a **Registry-Backed Overlay Templating System**. Rather than relying on native build tools for the initial scaffold, or statically embedding files in the binary, it will act like a scaffolding package manager that fetches and layers template directories from Git registries.

### 4.1. Core Concepts
* **Remote Repositories & Registries:** Blueprints are not embedded in the CLI. Instead, they are hosted in remote repositories (e.g., Git repos or a registry index). The CLI will support an "official" default repository alongside custom 3rd-party repositories.
* **The Registry Directory Convention (`pieces/`, `pies/`, & `pieces.lock`):** Any repository acting as a registry (including the official `bakery` repo itself) must adhere to the following root structure:
    * `pieces/`: Contains a folder for each individual piece provided by the repo.
    * `pies/`: Contains declarative `.yml` files defining pre-configured pies (e.g., `web.yml`, `cli.yml`). The CLI scans this directory to know what pies are available.
    * `pieces.lock`: A mandatory cryptographic lockfile generated by the registry maintainers. It contains the expected checksums/hashes for every piece in the repository to guarantee transport security and prevent tampering. The lockfile maps piece names to a single stable hash of the entire piece directory. Pie files are excluded from this hashing.
* **Base Pies & `piefile.yaml`:** A "Pie" is defined by a declarative YAML file. In a registry's `pies/` folder, these files can be named anything. However, when a project is actually scaffolded, the state file generated in the project root is strictly named `piefile.yaml` so the CLI can automatically recognize it for future operations.
* **The `piece.yml` Definition:** Inside each piece's directory, there is a `piece.yml` file. This file acts as the source of truth for the piece, containing its metadata (name, description, author), its dependencies (`depends_on`, `provides`), ecosystem actions, and the exact `huh` question configuration required to prompt the user for this piece.
* **Template Overlays:** Alongside the `piece.yml`, the piece directory contains a `template/` folder holding the actual overlay files. There is no global "templates" directory; everything is scoped to the individual pieces.
* **Piece Resolution Syntax (Git Refs & Local Paths):** Because the CLI supports multiple registries simultaneously, piece references inside dependencies and piefiles must include their repository source. Pieces do not have artificial "versions"; they are strictly tied to Git refs or local paths.
    * *Latest branch:* `user/repo:piece` (e.g., `bakery/core:react`)
    * *Specific Git Ref (Branch/Tag/Commit):* `user/repo/tag_or_commit:piece` (e.g., `bakery/core/v2.1:react` or `bakery/core/3a5f8b:react`)
    * *Local Directory (for development/testing):* `file:///path/to/repo:piece` or via configured local alias (e.g., `my_local_repo:piece`)
* **Piece Dependency Graph:** "Pieces" are formally defined in their `piece.yml` with explicit dependencies.
    * **Array Support:** Dependencies are defined as arrays, allowing a piece to depend on multiple other pieces simultaneously.
    * **Mutually Exclusive Dependencies:** To handle choices like React vs. Angular, pieces will use a "Capabilities" model (e.g., both pieces `provide: frontend-framework`). Other pieces can depend on the capability, and the CLI will enforce that only one piece providing a specific capability can be active at a time.
* **The Layering Process & Templating Engine:** When generating a project, the CLI downloads the requested pieces (resolved to exact Git commits), copies the base pie directory, and then overlays the directories for enabled pieces. During this copy process, every file is passed through Go's standard `text/template` engine. This allows files to use standard template variables (e.g., `{{ .ProjectName }}`) for dynamic module paths, or conditional blocks (e.g., `{{ if .HasSQLC }}`) to conditionally render imports or initialization code. Note that this `text/template` processing applies to file *contents* only; file and directory *names* use a separate, restricted `__Variable__` token substitution (initially `__ProjectName__`) documented in the design document.

### 4.2. Tool Execution
Native tooling (`go mod tidy`, `pnpm install`) will only be executed at the *very end* of the process to download dependencies and format the codebase, rather than being used to generate the files themselves.

**Pros of this approach:**
* Massively simplifies the Go logic (mostly just recursive file copying and template execution).
* Fully decouples the CLI binary from the boilerplate contents, meaning users can get new/updated pieces without upgrading the CLI itself.
* Fosters a community ecosystem where users can build and share their own custom 3rd-party Pieces and Pies via remote repositories.

### 4.3. State Management (Piefile & Pielock)
When a project is successfully scaffolded, the CLI will output two state files into the root of the generated project (intended to be committed to version control):
* **`piefile.yaml`:** Contains the list of enabled pieces and the specific "answers" the user provided during the interactive flow. 
* **`pielock`:** A lockfile capturing the exact, resolved Git commit hashes of every piece fetched from the registries during scaffolding.
* *(Note: This state management lays the groundwork for future features, such as running `bakery upgrade` to update a project's scaffolding. The exact schema for both files will be defined during the design phase).*

## 5. CLI Interface & Project Path Resolution
The primary command structure for scaffolding a project will follow the pattern:
`bakery init <pie> <project-name>`
*(Where `<pie>` could be a built-in alias like `web`, a local path to a custom `piefile.yaml`, or an HTTP URL to a remote Piefile).*

The `<project-name>` argument is dynamic and dictates where the project is created. The CLI must handle the following logic to resolve the target directory:

### 5.1. Handling Existing Directories (Path Provided)
If the argument is `.` or resolves to an existing relative/absolute path:
* **Empty Directory:** If the directory is completely empty, initialization proceeds immediately.
* **Non-Empty Directory:** The CLI will check the contents against a **configurable list of allowed files/directories** (e.g., `.git`, `.gitignore`, `README.md`, `LICENSE`).
    * If the directory contains *only* allowed items, initialization proceeds, ensuring these files are not overwritten.
    * If the directory contains non-allowed files, the CLI pauses and explicitly requests user confirmation before initializing inside the non-empty directory.

### 5.2. Handling Non-Existent Paths
If the argument looks like a relative or absolute path (e.g., containing slashes) but the path does not exist on the filesystem:
* The CLI will prompt the user to confirm if they want the directory structure created.
* Upon confirmation, the directories are created, and initialization proceeds.

### 5.3. Handling Standard Project Names
If the argument does not look like a path (e.g., a simple string like `my-app`) and no directory with that name exists in the current working directory:
* The CLI will automatically create a new directory named `<project-name>` in the current working directory.
* Initialization proceeds inside the newly created directory.

## 6. Configuration (Bakery CLI)
The Bakery CLI itself will use [koanf](https://github.com/knadh/koanf) for its configuration management. 

This configuration system will be used to manage settings such as the "allowed list" of files/directories for non-empty target paths. 
* **Defaults:** The CLI will have a built-in default list of allowed files (to be determined during the design phase).
* **Overrides:** Users can override these defaults through a cascading configuration system powered by `koanf`, supporting:
    * Configuration files (e.g., `.bakery.yaml` or similar).
    * Environment variables.
    * Custom CLI arguments (e.g., a flag to specify a custom allowed list file path).

## 7. Initialization Flow (Interactive vs. Defaults)
When a user runs the initialization command (e.g., `bakery init web <project-name>`), they trigger a specific "flow" based on the selected Pie. A "flow" is defined as a series of configuration questions asked prior to scaffolding the project (e.g., "Do you want koanf as your config library?", "Do you want TailwindCSS enabled?").

### 7.1. Interactive Prompts
* By default, the CLI will enter an interactive mode, asking the user these questions one by one.
* The CLI will use the **[huh](https://github.com/charmbracelet/huh)** library (by Charmbracelet) to render modern, user-friendly forms for these interactive questions.
* **Dependency-Driven Tree Structure:** The prompt flow will function as a dynamic decision tree generated automatically from the **Piece Dependency Graph**. The questions themselves are not hardcoded in the CLI; they are extracted dynamically from the `piece.yml` files. Pieces without dependencies act as the "roots" of the tree, and their subtrees are toggled on/off dynamically based on the current state of answers.
* **Pre-answered Piefiles:** A `piefile.yaml` can optionally contain pre-filled answers for its pieces. If a user initializes a project using a Piefile that already has all answers provided, the CLI will run completely silently and bypass the interactive prompts.
* The exact schema of the `piece.yml` (and how it defines its `huh` question) will be clarified during the design phase.

### 7.2. The `--defaults` Flag
* The CLI will support a `--defaults` argument that completely bypasses the interactive prompts.
* When provided, the CLI will automatically initialize the project using the default values for the given flow.
* **Configuration Integration:** The base default values for each question can be overridden globally using the `koanf` configuration system (env variables, config file). 
* **Always On:** The `--defaults` behavior itself can be set to "always on" via the `koanf` config, enabling completely non-interactive runs by default without needing to pass the flag manually.

## 8. Scaffolding "Pieces"
To facilitate the interactive flow, the scaffolding process is broken down into modular "pieces." The user can opt in or out of these pieces during the `bakery init` flow, or select a predefined "Pie" that bundles mandatory pieces together.

### 8.1. Common (All Pies)
* **Cobra Root (Mandatory):** Base `main.go` (at project root) and `cmd/root.go`. This is injected into every project without prompting.
* **Configuration (Mandatory):** `koanf` integration for reading settings from files/env.
* **Structured Logging (Mandatory):** Configured `slog` integration. All boilerplate code will utilize this logger by default.
* **Nix Flake:** Generates a root `flake.nix` (and `flake.lock`) along with a `nix/` directory for modular configurations. If other features (like Systemd) are requested, their specific Nix configs (e.g., `nix/systemd.nix`) will be generated in this directory and imported into the main flake.
    * **Direnv (Optional):** If Nix is enabled, users can optionally generate an `.envrc` file containing `use flake` for automatic environment activation.
* **Base Repository Files:** Standard `.gitignore`, `README.md`, and `LICENSE`.
* **CI/CD & Dependency Management (Optional):** Generates `.github/dependabot.yml` and GitHub Actions CI workflow files. The configurations dynamically adapt to the project type (e.g., `npm` vs `gomod`). *Note: GitHub Actions will use standard runners and deliberately exclude Nix to keep CI pipelines simple and universally accessible.*
* **Go Linter (Optional):** Configuration for `golangci-lint` (`.golangci.yml`). If CI/CD is also enabled, a linting job will be automatically added to the GitHub Actions workflow.
* **Database & SQLC (Optional):** Initialization of `sqlc` (`sqlc.yaml`) for type-safe database queries. SQLite is the default database engine; if enabled, the CLI will automatically install the `modernc.org/sqlite` driver.
* **Migrations (Optional, Conditional):** If the Database/SQLC option is enabled, the CLI will optionally prompt to include `pressly/goose` for managing database migrations.
* **LLM Agent Support (Optional):** Scaffolds support for AI agents (e.g., configuring project-specific agent rules, skills, and prompts). Enabling this unlocks a conditional subtree of further agent-configuration questions.
* **Release Pipeline (Optional):** GoReleaser config (`.goreleaser.yaml`) for automatically cross-compiling, packaging, and distributing the final binary (or Docker image) via GitHub Releases.
    * *Conditional Prompt:* If enabled, the user will be asked to select the target Operating Systems and Architectures (restricted to `amd64` and `arm64` for now) to configure in the pipeline.
* **Documentation Boilerplate (Optional):** Generates a `docs/` directory populated with stub markdown files (e.g., `requirements.md`, `schema.md`, `protocols.md`, `design.md`). 
    * *Conditional Generation:* The exact list of files and their structural contents will dynamically adapt based on other enabled features (e.g., `schema.md` is initialized for database schemas if `sqlc` is enabled; `protocols.md` is initialized for ConnectRPC protobufs, standard JSON APIs, or custom protocols depending on the project type and config).
* **Versioning (Mandatory):** All generated projects will initialize with a default semantic version of `0.1.0`. This version string will be automatically injected into `flake.nix`, `package.json`, and anywhere else a hardcoded version is required.
* **DX: Release Script (Optional):** Generates a local bash/sh script (`scripts/release.sh`) to automate version bumping. The script accepts a mandatory argument (`patch`, `minor`, or `major`), increments the version everywhere, commits the changes to a new release branch, pushes to the remote, and (if the GitHub CLI `gh` is installed) automatically creates a PR.

### 8.2. CLI Pie
* *(Currently, all core CLI features are covered by the Common pieces, but this section remains for future CLI-specific modules).*

### 8.3. Daemon Pie
* **Cobra Entrypoint:** A `serve` command (attached to the mandatory root command) to start the long-running process.
* **Graceful Shutdown:** Boilerplate context handling to catch `SIGTERM`/`SIGINT` and shut down safely.
* **Docker Support (Optional):** Generation of a `Dockerfile`, `.dockerignore` (to restrict build context size), `compose.yml`, and an example `.env` file (to encourage passing variables via `.env` rather than hardcoding them). Enabling this unlocks the following conditional prompts:
    * **s6-overlay support:** Scaffolds a `rootfs` directory and injects installation steps into the Dockerfile.
    * **Gluetun VPN support:** Configures the `compose.yml` to route the service through a `gluetun` VPN container.
* **Systemd Support (Optional):** Creates a standalone `.service` file (unless Nix Flakes are enabled, in which case it generates `nix/systemd.nix` to be imported by the main flake).

### 8.4. Web Pie
* **Frontend Foundation (Modular Piece):** The frontend framework is treated as a modular piece (e.g., `react`), initialized via Vite in the `web/` directory. This keeps the core architecture framework-agnostic.
* **Go Backend & Web Server:** A Go backend running [Echo v5](https://github.com/labstack/echo) (attached to Cobra) to serve the frontend assets and API routes.
* **Graceful Shutdown:** Boilerplate context handling to catch OS signals and gracefully shut down the Echo server.
* **RPC Communication:** Uses `connectrpc` for communication between the Go backend and React frontend. Configured to use binary mode in production and text/JSON mode in development for easier debugging.
* **Single Binary Embedding:** Uses `go:embed` to package the Vite build artifacts (the React frontend) directly into the Go binary, resulting in a single deployable file.
* **Docker Support (Optional):** Generation of a `Dockerfile`, `.dockerignore` (to restrict build context size), `compose.yml`, and an example `.env` file (to encourage passing variables via `.env` rather than hardcoding them). For Web projects, this automatically scaffolds a health monitoring endpoint in the Go backend and wires up a `healthcheck` section in the `compose.yml`. Enabling this also unlocks the following conditional prompts:
    * **s6-overlay support:** Scaffolds a `rootfs` directory and injects installation steps into the Dockerfile.
    * **Gluetun VPN support:** Configures the `compose.yml` to route the service through a `gluetun` VPN container.
* **Systemd Support (Optional):** Creates a standalone `.service` file (unless Nix Flakes are enabled, in which case it generates `nix/systemd.nix` to be imported by the main flake).
* **Styling:** Injection of TailwindCSS into the Vite React project.
* **Frontend Linter/Formatter (Optional):** Initialization of [Biome](https://biomejs.dev/) (`biome.json`). If CI/CD is also enabled, a Biome verification job will be automatically added to the GitHub Actions workflow.
* **TanStack Libraries (Optional):** A prompt allowing the user to select specific `@tanstack` libraries (e.g., Router, Query, Table) to configure in the React project. The exact list of available libraries will be expanded during the design phase.

## 9. Quality Assurance & Testing
Given the complexity of the registry-backed dependency graph and dynamic templating engine, the `bakery` CLI must be built with extreme stability in mind:
* **Unit Testing:** Comprehensive test coverage for the dependency resolver, prompt tree generation, and template execution logic.
* **Integration Testing:** End-to-end tests that mock remote registries and verify that generated pies successfully compile, format, and pass their own tests immediately after scaffolding.

## 10. Target Audience
* **Human Developers:** Needs a user-friendly, interactive interface for flows, with prompts for non-empty directories.
* **AI Agents:** Must support non-interactive execution via the `--defaults` flag (or config overrides) and explicit arguments for seamless automation.
